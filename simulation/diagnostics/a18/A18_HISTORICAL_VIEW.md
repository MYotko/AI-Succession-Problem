### Amendment A18, 2026-11-02: reading a producing identity's sealed history at the successor identity

**Where this text lives, and why it is not in the design note.** A17 section 6 item 3 binds the execution checkout to A17's adopted commit and its exact note, and the suite enforces that literally: `test_successor_constants_are_set_to_the_adopted_a17_commit` requires the working-tree note to be byte-identical to the note at the pinned commit `3b8d8261`. Amending the note in place would therefore move the current A10 pin, which this amendment has no reason to do and which would make every current A10 launch re-verify against a new commit. So A18 is committed as its own document, in the pattern of A17's committed companion `simulation/diagnostics/a17/A17_HOSTS_FEASIBILITY.public.md`, and `table_compatibility_A2.json` cites it by path and SHA-256. It folds into the design note the next time the current pin moves for its own reasons.

**Status and verdict.** Draft version 5, for the operator's adoption. Narrow execution support, proposed because A14's stated exception does not cover what the A11 compatibility proofs actually need. It authorizes one exception to the output-containment guard in `artifacts.scoped`, for an A11 or A12 compatibility proof that must read a producing identity's sealed A14 or A16 history from the checkout that staged it. It changes no scientific byte, seed, sample, comparison, budget or host authority, and it does not move the current A10 pin. Adoption grants no launch go.

**The problem it exists for.** A sealed A14 or A16 history inventory freezes every copy destination as an absolute path inside the checkout that staged it. Both `history_a14.History` and `history_a16.History` resolve each of those destinations through `artifacts.scoped`, which refuses any path outside the running `simulation/v3`. An A11 compatibility proof runs at the successor identity, in a different checkout, so a producing identity that carries a sealed history could not be proven at all. On 2026-11-01 and 2026-11-02 this refused the third of three planned records two seconds after launch, after the first two had been built over 18.4 X2-hours, and the repair's own identity change then voided those two.

**Why A14's exception does not cover it.** A14's snapshot-path repair stages hash-verified read-only copies **inside** the authorized write scope and preserves original input paths through verified aliases (design note line 2569). This exception does the opposite: it resolves paths that lie outside that scope. A14 also states that A14 alone admits the snapshot-path repair (line 2581), which ties that exception to A14's own authority rather than stating a principle a later amendment may invoke. A17 is a host amendment and authorizes no general write-boundary exception. The first version of this repair cited A17's adoption commit `3b8d8261` on the author's reading that the two were the same species. A blind review across model families found that reading unestablished and found the repair's central claim false, and the operator decided on 2026-11-02 to carry the exception by its own amendment instead.

**What is authorized, exactly.**

1. **The declaration.** `artifacts.historical_view(roots)` declares existing historical copy trees outside the running checkout, for the duration of a context. Each root must be absolute, must resolve to an existing bounded directory, and must not contain or lie inside `simulation/v3`. With nothing declared, containment is unchanged everywhere.
2. **What resolves.** Inside the context, a path under a declared root resolves if, and only if, it is an existing directory or an existing file with no write bit set. A missing copy, or a writable one, still refuses.
3. **Resolution is not permission to write.** Every write helper reached on the proof path resolves through `artifacts.write_scoped`, which refuses a declared root outright: `atomic_json`, `lease`, `snapshot_a11.receive` and `compatibility_shards_a11.stage_inputs`. `worker_safety.metadata_json` and `persist_restarts` write through `atomic_json` and are covered by it. `compatibility_shards_a11.write_once` carries no guard and needs none: it creates exclusively, so it cannot replace an existing copy, and a path that does not exist is not an immutable copy, so containment refuses it before any declaration is consulted.
4. **No claim is made that nothing in the tree can write under a declared root.** Three successive versions of this amendment claimed something of that shape and each was refuted by blind review: that resolution alone made a root read-only; that the two frozen stagers were the only residual writers; and that a test enforced the declaration's scope, which fell to an import alias, an attribute-form context set, an unlisted writer and a one-level indirect call. About 126 calls across 88 module-and-function pairs resolve a path through `scoped`, and many of them write: `production_runner.write`, `table_validation_a4.publish`, `budget_a6.append_consumption`, `service.command`. Guarding them all would be a tree-wide change touching several A2 boundary files, and is not proposed here.

   What is true, and all that is claimed: while a declaration is active the only code running is one recovery. `_HISTORICAL_VIEW` is set only by `historical_view`, whose only production caller is `replay_a16.original_validation_plan`. That call path was reviewed and writes nothing. **This is a reviewed property of one call path, not an invariant**, and no test can soundly make it one, because proving that nothing writes inside a dynamic scope needs whole-program reachability.

   What is enforced instead is narrower and sound. `test_the_write_helpers_resolve_through_the_guard` checks that the helpers in item 3 route through `write_scoped` and that `write_once` still creates exclusively. `test_the_scoped_call_sites_are_a_frozen_inventory` pins the exact set of resolver call sites by module and function, counting aliased and attribute forms, so a new resolver cannot appear without failing a test and forcing whoever adds it to say whether it writes. Both are mutation-tested against the real tree. The second does not say a declared root is unwritable; it says the set of things that could become writers has not changed without review, which is the same control as the A2 boundary pin.
5. **The residual, stated rather than closed.** `history_a14.stage_history` and `history_a16.stage_history` write and `chmod` through `scoped`. Both are frozen modules under their suite pins and cannot be guarded without breaking those pins. **They are not symmetric.** A16 confines every destination to the view root it is given and refuses anything outside it. A14 takes no view-root argument at all and checks destinations only against source paths, original directories and protected anchors; an earlier version of this amendment claimed otherwise and was wrong. A proof constructs `History` rather than staging, so neither is called on the proof path. This amendment does not authorize calling either with a declared root as its view root.
6. **What the copies are still bound by.** The inventory's own per-file size and SHA-256, checked by both `History` verifiers, which independently require every copy to be read-only. Every proof input is enumerated and hash-checked by the portable inventory. The exception widens where a read may resolve; it admits no unverified bytes.
7. **The roots' provenance is recorded, not asserted.** A root reached through a source's sealed specification is hash-bound by that specification's `historical_roots_sha256`. The helper does not itself read `identity.json`; `collect_record` separately requires each source root's `identity.json` to carry the producing code hash and the specification's own digest, so the identity binding holds for a successful record collection rather than for the helper in isolation. A root supplied by the plain sources document is normalized and nothing more. The record keeps the two apart in `execution.historical_view_provenance`. The first version of this repair claimed every root was specification-bound, which was false for the second kind.
8. **The A14 replay binding.** `replay_a16.original_validation_plan` now requires a registered A14 extension plan's `original_plan_hash` to equal the original plan's own `plan_hash`. This is an added refusal on a path that previously had none. It changes no job, no seed and no comparison byte.

**The pin record.** `artifacts.py` is one of the seven approved boundary files in `table_compatibility_A2.json`. The re-pin names this amendment as its authority, moves only `v3/artifacts.py`, preserves the previous approved hash and leaves the boundary set and every unchanged dependency as they were. `verified_record()` verifies hashes and does not validate an authority claim; that is this amendment's job.

**Verification required before adoption is relied on.** The repair's own claims are checked by tests in the suite rather than asserted in prose. The claims are the narrow ones stated in items 3 to 5, not a universal guarantee: that each write helper named in item 3 refuses a declared root, including replacing an existing read-only copy, which is the case that succeeded before this repair; that the writers named in item 4 as unguarded stay unguarded, so this text cannot drift from the code; that the set of resolver call sites is unchanged; that the declaration resolves only existing immutable copies; that it does not leak past its context; and that both an A14 and an A16 sealed history load at a successor identity through `replay_a16.original_validation_plan`. A full pin sweep and the full suite run after the repair, not only the tests that cover it.
